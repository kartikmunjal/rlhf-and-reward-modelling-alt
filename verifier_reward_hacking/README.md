# Extension 16: Programmatic-Verifier Reward Hacking

## Honest status

**Preregistered; the candidate pool and trusted mutation audit are built, but
the base-model eligibility gate, final task selection, pilot, and training have
not started.**

This extension asks whether GRPO learns to exploit incomplete visible unit tests
and whether mutation- and property-based verifier hardening improves genuinely
held-out correctness. The design, endpoints, seeds, task split, sandbox gates,
and analysis rules are frozen in [`PREREGISTRATION.md`](PREREGISTRATION.md).

The eventual study is limited to Qwen2.5-0.5B-Instruct with LoRA on 200 Python
function tasks. It will not support claims about frontier models, vendors,
production sandbox security, or GRPO in general.

Results will be generated from committed JSON artifacts after all integrity
gates pass. No expected or simulated result table is provided here.

The candidate-pool counts and cryptographic hashes are generated by
`scripts/build_verifier_candidates.py` and recorded in
`data/processed/verifier_reward_hacking_v1/candidate_manifest.json`. Hidden
tests, reference solutions, mutation details, and raw model outputs remain
gitignored to prevent evaluation leakage.

## Reproduction sequence

1. Build the pinned sandbox image and run `scripts/run_verifier_sandbox_gates.py`.
2. Run `scripts/run_verifier_base_qa.py`; it is resumable at the sample level.
3. Freeze the eligible corpus with `scripts/prepare_verifier_study_data.py`.
4. Run the separately logged C1 pilot and bounded dev tuning.
5. Run `scripts/train_verifier_grpo.py` for C1–C4 and all three locked seeds.
6. Evaluate C0 and every final adapter with `scripts/evaluate_verifier_policy.py`.
7. Generate confirmatory statistics with
   `scripts/analyze_verifier_reward_hacking.py`, then prepare and complete the
   blinded audits with `scripts/prepare_verifier_manual_audits.py` and
   `scripts/analyze_verifier_manual_audits.py`.

Every model-dependent command requires a passing sandbox-gate manifest for the
same pinned image. Confirmatory training refuses a changed optimizer-step
budget, and analysis refuses incomplete or hash-mismatched ledgers.
